AGENTIC AI · MINI-PROJECT

FoodieAgent project guide

Architecture, implementation notes, original problem statement, memory, tool-calling, and collaborative-agent features, evaluation formula, and a five-minute jury demonstration.

ORIGINAL PROBLEM STATEMENT · KEEP UNCHANGED

“Order a vegetarian pizza under ₹500 delivered within 30 minutes.”

The agent understands preferences, searches restaurants, retrieves menus, compares options, places a simulated order after explicit approval, tracks status, and notifies the user.

PERSISTENT MEMORY & TOOLS

Long-term memory and tool calling

Persistent memory

The hosted version persists preferences in a project database. The local source version uses SQLite. Preferences include dietary choice, cuisine, budget, delivery limit, preferred restaurant, and spice level. Saving requires an explicit choice; current request values always win.

Callable tools

Restaurant search, menu retrieval, vegetarian filtering, exact total calculation, delivery-estimate checking, confirmed order creation, order-status retrieval, and persistent notifications execute against the catalogue or database.

COLLABORATIVE AGENTS

Role-based collaboration

1Preference Agent: parses the present request and optionally fills missing fields from stored memory.
2Restaurant Discovery Agent: finds catalogue restaurants and checks open/service-area metadata.
3Menu & Dietary Agent: retrieves menu rows and validates explicit vegetarian metadata.
4Price & Delivery Agent: calculates subtotal, delivery fee, assumed 5% food tax, and ETA eligibility.
5Coordinator Agent: combines agent outputs, enforces hard constraints first, and ranks eligible candidates.
6Order Monitoring Agent: reads persisted order state and writes in-app notifications for each allowed transition.

Collaboration is inspired by a simplified Contract Net workflow: the coordinator distributes subtasks, gathers proposals, applies constraints, and selects the best eligible option. It is not a full FIPA-ACL implementation.

EXPLAINABLE DECISION

Ranking formula and hard constraints

40% · Price
Price score measures headroom below the maximum budget.
35% · Delivery
Delivery score measures time headroom against the deadline.
25% · Rating
Restaurant rating normalized to a 0–100 scale.

Composite score = 0.40 × price score + 0.35 × delivery score + 0.25 × rating score. Scores are used only after the item passes the explicit vegetarian requirement, restaurant/item availability, total budget, and delivery deadline. Total = food subtotal + delivery charge + an assumed 5% tax on the food subtotal. All monetary calculations use integer paise.

WORKFLOW

Five-minute demonstration

  1. Run the prefilled jury request from Discover.
  2. Point out extracted constraints and the saved-memory opt-in.
  3. Show the separate specialist agents and the structured tool results.
  4. Compare eligible items, totals, delivery estimates, scores, and rejected options.
  5. Choose a result; review food subtotal, delivery, tax, and final amount.
  6. Check the explicit confirmation box and create a simulated order.
  7. Open Orders and advance status from Confirmed to Preparing, Out for Delivery, then Delivered.
  8. Open Notifications to show the persistent alert records.
  9. Save preferences, refresh/reopen the app, and show that the saved memory and history remain available for that browser profile.
LIMITATIONS

What the demo does not claim

The restaurants, menu prices, customer ratings, open status, delivery estimates, and offers are simulated. No live restaurant API, courier service, payment gateway, or external ordering system is connected. Order transitions are manual demonstration controls; there is no real background tracking. Food tax is an explicit simplified assumption, not tax advice.
